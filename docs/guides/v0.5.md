# BioMCP v0.5 release and validation

The v0.5.1, v0.5.2 and v0.5.3 feature increments are delivered together as package version 0.5.3.

## Expression reports — v0.5.1

The Expression tab renders an RNA and protein expression summary using validated HPA fields. Tissue RNA measurements retain their upstream units and values. Protein tissue specificity, staining reliability, secretome information and localization are displayed when available. Missing measurements read “Not reported.” Protein class is labeled separately from protein abundance.

MCP tool `gene_report(query, include_disease=False)` returns schema `biomcp.report.v1`, normalized identity, expression measurements with missingness, source URLs/timestamps, optional disease data and the full underlying research evidence. Existing tools retain their interfaces.

## Gene comparison — v0.5.2

Open the dashboard's Gene comparison and disease evidence tab. Paste up to 20 identifiers separated by commas or newlines and click Compare genes. The table updates as work finishes, preserving input order and duplicate rows. Full evidence is available in the report JSON.

Batch mode defaults to identity and HPA expression. Sequences and literature are excluded from comparison. At most two gene tasks execute concurrently across batches in a process. Duplicate inputs and identifiers resolving to the same gene share a report task within the batch. Ambiguous identifiers and unavailable sources appear as failed or partial rows. Cancellation cancels pending tasks.

MCP tool `compare_genes(queries, include_disease=False)` returns the completed batch using schema `biomcp.batch.v1`. It accepts a comma/newline-delimited string. The UI streams intermediate results. Input with more than 20 entries is rejected before provider calls, including repeated entries. Cross-process quotas still require the experimental Redis option.

## Disease evidence — v0.5.3

Select Include disease associations in the comparison tab, or pass `include_disease=True` to a new MCP tool. Open Targets returns up to 10 direct associations, provider scores, disease IDs/names, total available count and a source link. The UI table lists disease names and JSON includes scores and provenance. The report explicitly states that association scores summarize evidence.

Open Targets advises downloaded datasets for systematic multi-target work. Use this interactive feature for small exploratory comparisons. Large repeated comparisons require a local dataset adapter in a future version.

OMIM access is optional. Configure both variables in the launching environment only after arranging the appropriate API access/display rights:

```bash
export BIOMCP_OMIM_ENABLED=true
export OMIM_API_KEY='your_approved_key'
```

The key is sent as a request header. Licensed responses are not placed in the aggregate research cache. OMIM gene-map records retain gene and phenotype distinctions in report JSON. Missing configuration produces `not_configured`. A configured but failed provider produces `unavailable`, independently of Open Targets. Live OMIM validation requires an authorized key and remains unverified in this environment.

## Verify this release

```bash
python -m pip install -e '.[dev]'
python scripts/check.py
python -m pytest tests/test_reports.py tests/test_mcp_e2e.py -v
python app.py
```

The automated baseline is 33 tests. Tests cover input caps before network activity, duplicate/order/error handling, missing expression values, disease response mapping, OMIM gating and real MCP subprocess calls to both new tools. Provider calls in automated tests are mocked.

Live SPP1 validation returned a successful gene report, HPA expression and Open Targets direct associations. Disease and expression source status should be inspected independently. Hosted authentication, durable batch recovery and live OMIM access remain open deployment gates. Batches are interactive and in-process.

The UI exposes detailed per-gene evidence in expandable JSON, alongside the comparison table. Full interactive tissue charts, per-row detail pages and a retry-only-failed-stage workflow are follow-up improvements.
